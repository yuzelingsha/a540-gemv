# 失败尝试与负结果技术记录 (Failed Attempts & Negative Results)

本文件详尽记录在 Qualcomm Snapdragon 835 / Adreno 540 平台上，经过严格实测验证为**无效、劣化、伪优化或引发系统崩溃**的实验方案，严禁在工程与技术报告中粉饰数据。

---

## 1. 尝试 1：静态命令流回放 (Static Replay)
- **假设前提**：认为 OpenCL 每轮解码迭代的主机端 `clEnqueueNDRangeKernel` 发射开销过高，尝试通过录制并重放静态命令序列消除驱动开销。
- **实测结果**：端到端速度从 15.32 tok/s 变为 15.31 tok/s，**收益为 0.0%**。
- **硬件根因**：Qualcomm Adreno 540 的私有驱动内部已具备硬件级的 Ringbuffer 机制，驱动发射仅占不到 1.2% 的延迟；在用户空间额外挂钩静态回放增加了互斥锁与同步等待开销，完全抵消了微弱的指令流发射优化。

---

## 2. 尝试 2：激进循环展开 (Aggressive Loop Unroll)
- **假设前提**：在 GEMV 的 $K$ 维累加循环中加入 `#pragma unroll 8` 或 `#pragma unroll 16`，期望降低分支跳转指令开销。
- **实测结果**：解码吞吐量从 15.32 tok/s 骤降至 **13.42 tok/s (性能劣化 -12.4%)**。
- **硬件根因**：Adreno 540 每个着色器处理器的标量寄存器空间有限。展开导致每个线程的活向量激增，触发编译器将寄存器溢出 (Spilling) 临时刷写至低速全局显存，导致每个 SP 的活跃并发度 (Occupancy) 从 4 Wavefront 下降至 1 Wavefront。

---

## 3. 尝试 3：LM-Head 零点消除 (LM Zero-Point Removal)
- **假设前提**：理论推导证明，在词表输出投影矩阵的反量化计算中，减去零点偏移在数学上可以通过离散常量归纳优化，减少数百万次半精度减法。
- **实测结果**：端到端吞吐量测试在 5 次复测下呈现 15.32 ± 0.09 tok/s，**无统计显著收益**。
- **硬件根因**：MiniCPM 词表大小为 130,560，LM-Head 是绝对的内存带宽受限算子（计算强度 < 0.1 FLOP/Byte），瓶颈在从 LPDDR4x 读出矩阵权重，ALU 计算周期的缩减在总时间开销中被全面掩盖。

---

## 4. 尝试 4：朴素 y4 拓扑重排破坏结合律 (Naive y4 Topology)
- **假设前提**：沿 $Y$ 维度单线程连续加载 4 个权重的向量指令，提升内存突发传输效率。
- **实测结果**：微基准算子测试速度大幅上升（折合 17.30 tok/s），但在端到端自回归测试中：
  - **第 3 个 Token 发生数值发散**；
  - 生成文本在 5 步之内退化为乱码或重复无意义 Token。
- **硬件根因**：半精度浮点数不具备结合律，重排求和树拓扑导致累积误差迅速突破 Softmax 分流阈值，是必须杜绝的“伪性能优化”。

---

## 5. 尝试 5：激进规约 add-y4 破坏长序列精度 (add-y4 Long Sequence Divergence)
- **假设前提**：在 `o_proj` 与 `down_proj` 上采用 `add-y4` 激进规约方案以压缩计算用时，单步时延降至 52.77 ms (18.95 tok/s)。
- **实测结果**：在 64/128 Token 短测试表现稳定，但在 512 Token 全长测试中：
  - **在第 187 步出现数值分流发散 (First Divergence Step = 187)**；
  - 最终生成的长文本与基准真值出现关键 Token 不一致。
- **结论与处置**：在 100% Bit-Exact 约束下，任何改变浮点规约顺序的优化均不可上线，生产主推必须维持严格保序的 `q-VRL` 方案。

---

## 6. 尝试 6：Kryo 280 Gold 2.4576GHz 极限锁频引发电压骤降 (Voltage Sag Crash)
- **假设前提**：将大核（Core 4~7）强制锁定在高通标称最大频点 2457600 kHz (2.4576 GHz)，以期彻底消除 CPU 前处理与调度气泡。
- **实测结果**：高负载解码持续 10~30 秒内，CPU 遭遇瞬时欠压崩溃，进程报 `Segmentation fault (exit code 139)` 硬死机退出。
- **硬件根因**：老旧骁龙 835 (Xiaomi MIX 2) 供电模组老化，在 GPU 710MHz 全负荷与 CPU 2.4576GHz 并发瞬态突变下，供电轨产生瞬时电压跌落 (Voltage Sag)；
- **解决措施**：将大核保守锁频在 2361600 kHz (2.3616 GHz)，历经 512 Token 全长压测零报错，确立了硬件稳定频率红线。

---

## 7. 尝试 7：大核亲和性绑定与 GPU 驱动中断冲突 (Interrupt Contention)
- **假设前提**：将 LiteRT 推理循环绑定在大核群（掩码 `0xf0`），直觉认为大核算力更充裕。
- **实测结果**：每步生成时延产生 1~2 ms 的随机抖动（Jitter），帧率无法收敛稳定。
- **系统根因**：Linux 内核中 `kgsl_3d0`（高通 Adreno GPU 核心驱动中断服务程序）默认被路由并跑在大核上。LiteRT 主循环占满大核导致 GPU 完成中断被延迟处理，引发主机端反向等待；
- **解决措施**：将 LiteRT 主线程重绑定至小核（Core 2, 3，掩码 `0x0c`），释放大核专职处理高频驱动中断与显示管线，时延方差下降 85%。

---

## 8. 尝试 8：LM-Head 未暂存版全局内存广播 (Unstaged Activation Broadcast)
- **假设前提**：130,560 个全局线程直接通过 `read_imageh` 或全局指针读取 3072 字节隐藏层激活向量，依赖 L2/Texture Cache 自动缓存。
- **实测结果**：Stage D 耗时高达 **28.73 ms**，单算子拖慢近 11.5 ms。
- **硬件根因**：Adreno 540 的 L2/TP 缓存带宽无法承受 13 万个线程同时以细粒度非对齐方式并发命中，显存控制器总线发生严惩仲裁碰撞与拥塞；
- **解决措施**：引入 LMS 工作组协作暂存（Stage D Opt 2），64 线程协作一次性加载 384 个 `half4` 到片上片内存储，耗时骤降至 **17.21 ms**，净省 11.52 ms。

---

## 9. 尝试 9：3072 字节激活向量放入 Constant Memory (__constant)
- **假设前提**：利用 OpenCL `__constant` 内存修饰符声明隐藏层激活向量，期望利用 GPU 专有常量缓存（Constant Cache）实现广播。
- **实测结果**：实测单算子耗时 **19.82 ms**，明显劣于 LMS 协作暂存的 **17.21 ms**。
- **硬件根因**：Adreno 540 的 Constant Cache 广播机制在超过 1KB 且工作组规模较大时，存在单时钟周期的广播位宽限制，依然存在隐式指令流水停顿，不如程序员显式管理的 Local Memory 可控高效。

---

## 10. 尝试 10：Local Memory 树状规约切除 261KB FP16 Logits 显存写回
- **假设前提**：在 GPU 上用 Local Memory 直接执行两阶段 Top-1/Top-K 树状规约，彻底消除向全局显存写回 130,560 个 FP16 Logits (261 KB) 的开销。
- **实测结果**：在驱动内部编译阶段触发 Adreno 540 (2019 原厂驱动) 私有编译器崩溃（Driver Internal Crash），无法生成目标机器码。
- **硬件根因**：老旧闭源驱动对跨工作组的大规模半精度规约内联支持存在缺陷，权衡稳定性与可行性，此路径被正式标记为不可行。
